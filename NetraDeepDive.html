0. What this covers

This document describes the Netra 2.0 backend exactly as it is in the nine text exports of the repository (netra_part1.txt to netra_part9.txt). Every file path, setting, threshold and model call below was read from that code. Where the code and its own docs disagree, the code wins and the gap is called out. Your actual .env is not in the bundle, so settings are quoted from .env.example and docs/SETUP.md (they match).

Not covered. The frontend is not in this bundle. Postgres, Qdrant, Entra and BaxiGuard behaviour is described from the client code only; nothing was run against live services. Items that need a live check are marked verify.

Replaces the earlier draft, which was written without reading the code.

1. At a glance

17platform modules under src/netra/modules
3apps: ask_hr, jde, uploads
2processes: API + worker (same package)
3LangGraph graphs on the ask path: ask, retrieval, SQL
5Qdrant collections: catalog, chunks, uploads, db_schema, answer_cache
9Postgres schemas owned by modules + infra
2-3LLM calls for a typical first HR question
150 srequest deadline in .env.example (code default 55 s)

Netra is a modular monolith. A question enters FastAPI, is authenticated into an AccessScope, and runs through a LangGraph ask graph: screen, load chat context, rewrite, curated-cache lookup, route, plan, dispatch to agents (document retrieval, SQL, chat uploads), compose a grounded answer, screen output, then write chat history and an audit row before replying. Documents reach Qdrant only through an approval step and a transactional outbox that the worker relays.

  • Each module: services/<x>_service.py (ABC) + one _impl.py; enforced by tests/architecture/test_boundaries.py.
  • import-linter contracts in pyproject.toml: modules never import apps or bootstrap; apps never import each other; models/services never import SDKs.

  • Expected negatives are Outcome (Ok / Miss(reason)), not None; failures are typed AppErrors mapped to HTTP by one boundary.

Entry points: POST /api/v1/chat returns one JSON envelope; POST /api/v1/chat/stream streams stage events and a final event. The stream runs the graph in its own task, so a client disconnect still records and audits the turn.

5. Every LLM call per query

All chat calls go through ModelGatewayServiceImpl.complete. Each call is retried once on timeout/unavailable, and complete_json adds at most one repair call if the output fails its Pydantic contract. Every call writes a row to model_gateway.llm_usage (tokens and cost, no prompt text). In .env.example and docs/SETUP.md both tiers map to claude-sonnet-4-6.

Ceiling for a document question with every branch taken: 12 calls (rewrite 2, route 2, plan 2, 3 retrieval rewrites, answer 1, groundedness 2), before transient retries.

Non-chat model calls per question

  • Embeddings (Ollama): 1 in the rewrite node + 1 per document/upload task (the sub-query is embedded again even when it equals the question) + 1 per retrieval rewrite.
  • Reranker: 1 per finish node run (up to 2 per task when a post-finish rewrite happens). If it is down, retrieval keeps vector order and confidence takes a 0.10 penalty.

Outside the ask path

  • SUGGEST_TAXONOMY (ingestion label stage), only with INGESTION__AI_SUGGESTIONS_ENABLED=true.
  • VALIDATE_METADATA: at most one SIMPLE call per validate-metadata run; security fields (Access_Tag, Country_Region, Audience_Designation) are never auto-applied.
  • SUMMARIZE exists but nothing calls it (Finding 7).

6. Document retrieval

  1. Mandatory filter (retrieval/search/filter_builder.py): domain in profile domains, status approved, is_current true, effective_from <= now, effective_to null or >= now, language; any of global / region / country; any of audience / access_tag. Optional version_ids (gate mode) and chat_id (uploads).
  2. Stage A, catalog (document_catalog): one point per document version, embedding of the catalog card (hierarchy, title, kind, applicability, keywords, summary, outline, "Answers:" questions). Soft taxonomy filters from routing/planning apply here only.
  3. Stage B, chunks (document_chunks): grouped by identity.version_id inside selected documents. Global search is added only when no document qualified, when widened, or in boost/off modes.
  4. Finish: rerank all candidates, keep 5, swap each chunk for its parent section text from Postgres (ingestion.parent_section), build Evidence with provenance (title, link, version, page, heading path).
  5. Every fallback level is recorded: 1 global scope, 2 widened, 3 rewritten.

Chunk embeddings use a context label: heading path or title, version, part i/n (ingestion/chunking/context_label.py).

7. Database (SQL) agent

  • Datasources come from config/databases.yml (passwords from <ID>_PWD). With no file, a demo SQLite data/jde_demo.db is created.
  • The sales_order skill is bound to the first datasource in the file: jde_skills(next(iter(datasources))) in container.py (Finding 9).
  • Table cards carry descriptions, notes, allowed values and exact per-dialect expressions for value conventions (Julian CYYDDD, x100, x10000, x1000) plus today's Julian value.
  • Over 40 tables, a zero-LLM lexical shortlist keeps 24 (name x3, column x2, notes x1) plus foreign-key neighbours.
  • Results are converted in Python as a safety net (SHTRDJ to SHTRDJ_date), passed to the answer model as pipe text (max 50 rows), and shown as a table block (max 20 rows).
  • SQL evidence gets retrieval strength 1.0 and counts as reranked, so SQL answers clear the bar on groundedness alone.
  • The database agent does not apply AccessScope row filters; it only refuses when allowed_tables is an empty set.

8. Answer, citations, confidence

confidence = 0.4 x retrieval_strength + 0.6 x groundedness - 0.10 (if not reranked) - 0.03 x max_fallback_level
bar        = NETRA_ANSWER__CONFIDENCE_BAR (0.72 in .env.example; code default 0.90)
           = NETRA_ANSWER__DEGRADED_CONFIDENCE_BAR when the reranker was down (0.62 in .env.example; code default 0.80)
  • The system prompt allows only numbered evidence; the model answers INSUFFICIENT_EVIDENCE when it cannot answer, which becomes NO_ANSWER.
  • Numeric groundedness (deterministic): every number, percentage, date and URL in the answer must exist in the evidence, compared by value (17,954.85 = 17954.85).
  • Citations are built by code from the [n] markers; unknown markers are stripped. No citations, or a score under the bar, returns the fixed LOW_CONFIDENCE message.
  • Ticket offer: shown when the status is not ANSWERED and the ticketing provider is available (placeholder provider in .env.example reports unavailable).

9. Ingestion and publication

  • Extraction: format detected from content signatures first. PDF/DOCX/PPTX use local parsers (PyMuPDF headings from TOC then font heuristics; python-docx styles; slides); OCR (Baxi Extract, RapidOCR or fake) is used for images, scanned PDFs without a text layer, and DOC/PPT without LibreOffice. XLSX/CSV become header-carrying rows. Embedded images are not OCR'd while EXTRACTION__OCR_IMAGES=false (current setting).
  • Eligibility: approved flag + approval date + is_current; otherwise the file is skipped. Unknown vocabulary values quarantine the file with the field named.
  • Version identity: SHA-256 of content + hash of the metadata row. Unchanged files are skipped.
  • Taxonomy precedence: human > source (path/title) > AI > default; disagreements are reported as needs_human_decision.
  • Publication: approve writes PUBLISHING and four outbox rows in one transaction; the worker projects into Qdrant and flips states. A unique index allows one LIVE version per document.

10. Access / RBAC seam

  • Static (current setting): tokens from config/access_fixture.local.yml; scopes expanded by apps/ask_hr/applicability.py (managers see employee and new-hire content; HR/admin see everything and get the hr_only group).
  • Entra: JWT validated against JWKS (RS256, audience, issuer, 60 s leeway); roles from the roles claim plus group_role_map. Scope comes from ChainScopeResolver: local override table, then directory attributes, else deny.
  • Admin routes check roles with access.require_role: ingestion runs need ADMIN; versions, documents and answer-cache need HR_CONTENT_OWNER; audit needs AUDITOR.
  • applicability.designation is stored and indexed in Qdrant but not part of the mandatory filter yet.
With NETRA_ACCESS__PROVIDER=entra, scope resolution cannot succeed yet. See Finding 4.

13. Findings from the code

Each item was traced in the source. Items 1, 2 and 4 affect correctness or access and should come before any caching work.

#What the code doesSuggested fixWhere
1high Superseded and withdrawn versions may stay searchable in Qdrant
_on_go_live marks the previous version only with lifecycle.superseded_by; its chunks keep applicability.is_current=true. _on_withdraw uses set_payload with the dot key applicability.is_current, and the comment in _on_go_live says this creates a flat top-level key in Qdrant instead of updating the nested field. The in-memory store resolves dot paths, so tests pass. ADR-0004 says go-live flips the old version off; the code does not.		Re-upsert the old version with is_current=False (as go-live does for the new one), or pass Qdrant's nested key. Verify by counting identity.version_id = old AND applicability.is_current = true after a re-ingestion.ingestion/services/publication_service_impl.py
2high Answer-cache invalidation targets the new version, not the replaced one
Approve enqueues ANSWER_CACHE_INVALIDATE with aggregate_id = new version_id. Curated entries link to the versions they were written from, so a replacement leaves old entries approved.		In _on_go_live, call invalidate_for_version(previous.version_id), or enqueue the event with the previous id.publication_service_impl.py, container._relay
3medium Curated answer entries are lost on restart
answer_cache.InMemoryEntryRepository() is used in every profile (README lists this as a known debt). Qdrant points survive, but lookup drops any id the repository no longer has.		Write a Postgres repository over the existing answer_cache.entry migration before enabling the cache.bootstrap/container.py
4high Entra scope resolution always denies
_entra_access builds MicrosoftGraphClient(graph, 5.0) if False else FakeDirectoryClient({}) and an empty in-memory override repository, so the chain (override, then directory, then deny) has nothing to resolve from and falls through to deny for every Entra user. The Graph client is also created without an auth header, and group_role_map is not set in .env.example. 5medium One COMPLEX planner call on every HR question (by design)
uses_model_planner returns true whenever a routed skill has a retrieval profile. This is deliberate: the planner maps everyday words to policy terms ("new fathers" to parental leave), which PROCESS.md test 5 relies on. It is still the largest repeatable cost per HR question, and config/model_routing.yml (plan_on_complex_for) is not read by any code.		Keep the planner but cache its output (section 14, step 2); remove or wire up model_routing.yml so the config is not misleading.orchestration/graph/nodes.py
6medium Both model tiers point to the same model
SIMPLE and COMPLEX are both claude-sonnet-4-6 in .env.example and SETUP.md, so routing, rewrite and chart calls cost the same as answers.		Point SIMPLE at a smaller model once access is approved, and add its row to config/model_costs.yml..env / settings
7medium Conversation summaries are never written
The summarizer is documented as refreshed by the worker, but worker.run_forever only relays the outbox and sweeps uploads. The domain summary stays empty, so follow-ups rely on the 5-turn window and ledger.		Schedule chat_history.refresh_summary from the worker, or drop the field.bootstrap/worker.py
8medium Expired rows in infra.cache_entries are never deleted
The Postgres cache says it is swept by the worker; no sweep exists. Reads treat expired rows as misses, so this only grows the table.		Add DELETE FROM infra.cache_entries WHERE expires_at < now() to the worker loop.infrastructure/cache/postgres_cache.py
9medium JDE skill uses the first datasource in databases.yml
jde_skills(next(iter(datasources))). In databases.yml.example the first entry is baxflex, so a copied file would send sales-order questions to the attendance database. config/skills/*.yml is not loaded.		Select the datasource by id (for example jde) or by domain jde_sales.bootstrap/container.py
10medium Deadline is longer than the proxy timeout
The request deadline is 150 s in .env.example; the IIS example sets the ARR timeout to 120 s, so slow answers can be cut by the proxy before the API returns. 14. Caching plan (code-grounded)

Order matters: a cache keyed on corpus state is only safe once old versions really leave the index.

Step 0: prerequisites

  1. Fix Findings 1 and 2 (currency flip and cache invalidation on supersede).
  2. Add a corpus generation: a counter in Postgres (for example a row in infra.cache_entries, namespace corpus) incremented by the relay after VERSION_GO_LIVE and VERSION_WITHDRAW. Use it as the version part of every answer-level cache key, so a publish makes old keys unreachable without a scan.

Step 1: turn on the curated cache properly (zero LLM calls on a hit)

  1. Write PostgresEntryRepository for answer_cache.entry (columns already exist; sources holds the linked version ids).
  2. Swap it in at container.py where InMemoryEntryRepository() is built.
  3. Set NETRA_ANSWER_CACHE__ENABLED=true; seed entries through POST /api/v1/admin/answer-cache/entries then /approve (HR content owner).
  4. Hits happen in cache_lookup, after rewrite and one embedding, before route/plan/answer. Audit still runs (outcome cache_hit).

Step 2: plan cache (removes the COMPLEX planner call on repeats)

# orchestration/graph/nodes.py, AskNodes.plan, around the planner call
key = build_key(f"plan:{ROUTING_CONFIG_VERSION}", "",            # plans do not depend on scope
                f"{standalone}|{decision.intent}|{','.join(decision.skills)}|{sorted(decision.taxonomy_filters.items())}")
# Cache namespace "orchestration.plan", TTL 86400, value = json of [(skill_id, sub_query, taxonomy)]
# Store only plans with source == "model" and at least one task.

The plan prompt contains the question, skill list and vocabulary glossary only, so one entry can serve every user. Inject the shared Cache into AskNodes from the container.

Step 3: embedding cache (cheap, safe)

Wrap ModelGatewayServiceImpl.embed: namespace gateway.embed, key build_key(embedding_model_id, "", text), TTL 7 days. The rewrite node and the document agent embed the same text when the plan keeps the question unchanged, so this also removes a duplicate call inside one request.

Step 4 (optional): generated-answer cache

  • Key: build_key(f"answer:{corpus_generation}", scope_hash, f"{application_id}|{domain}|{standalone}"). scope_hash keeps users with different access apart.
  • Store only when: status ANSWERED, no SQL evidence (live data), no upload evidence, rewrite.used_model is false (self-contained question), and confidence >= bar.
  • Check it in cache_lookup after the curated lookup; on a hit return the stored reply with its citations and mark cache:hit_generated in diagnostics.
  • Run in shadow mode first (look up and log, but do not serve) and compare against fresh answers.
  • Wrap the expensive path with SingleFlight on the same key to collapse simultaneous identical questions.

Step 5: housekeeping

  • Sweep infra.cache_entries in the worker (Finding 8).
  • Bump ROUTING_CONFIG_VERSION whenever config/vocabulary.yml changes; the plan cache uses the same version.
